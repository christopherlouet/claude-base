## Chosen Approach

### Sequencing

```
gh api verification (Phaser repo state)
            │
            ▼
Recipe entry draft ──┐
                     ├──▶ Hand-edit phase complete
Roadmap subsection ──┘
            │
            ▼
npm --prefix website run generate  (regenerates counts.json + README badge)
            │
            ▼
npm --prefix website test          (verifies generate-counts logic on new entry)
            │
            ▼
./scripts/validate-counts.sh + ./scripts/audit-base.sh
            │
            ▼
CHANGELOG bullet + grep for protected names + commit
```

### Rationale

- **Verify-first**: `gh api` lookup precedes the draft because the recipe's `Vendor-neutrality` paragraph must cite real stars, last commit, license — memory `feedback_verify_code_claims` is explicit.
- **Recipe before roadmap**: the roadmap rationale references the recipe ("vendor publishes a canonical skill — see recipe"). Writing the recipe first lets the roadmap reference real content.
- **Regenerate before validate**: `validate-counts.sh` reads `counts.json`; the generator must run first so the counter is at 17 when the validator runs.
- **CHANGELOG last**: keeps the diff clean and lets the bullet describe what actually shipped.

### Alternatives considered

| Alternative | Why rejected |
|-------------|--------------|
| Edit `counts.json` by hand to `17` | Generator overwrites it on next run; manual edit creates short-lived drift |
| Add Phaser entry to "Stack-specific" subsection of recipe | Resolved by clarification Q3 — main section, vendor canonical tier |
| Audit PixiJS + Kaplay alongside Phaser | Out of scope per spec; a separate marketplace-audit pilot is the right home if appetite emerges |
| Drop the CHANGELOG bullet (claim "doc-only, no entry") | The Keep-a-Changelog pattern in this repo lists every user-visible doc improvement; consistency wins |
