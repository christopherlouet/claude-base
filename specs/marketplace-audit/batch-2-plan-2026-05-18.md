# Marketplace audit — Batch 2 plan: `legal` + `growth` vs Anthropic built-ins

**Date**: 2026-05-18
**Status**: Plan only — pilots execute in follow-up sessions
**Scope**: Phase 1 remaining domains from `specs/marketplace-audit/spec.md` (`legal`, `growth`), audited against the **`anthropics/claude-plugins-official` catalog only**.

---

## Why batch 2 narrows the comparator

Batch 1 (4 pilots: `cli-tools`, `dev-*`, `qa-*`, `ops-*`) audited claude-base against the **whole marketplace** — vendor skills (Supabase, Prisma, Vercel, MongoDB, Grafana, Microsoft Playwright…) and community skills indistinctly. That breadth was right for those domains because vendor signal was high and noisy.

`legal` and `growth` are structurally different:

- **Legal**: domain experts (Sushegaad GRC, Claude Cowork Legal) live outside the `anthropics/claude-plugins-official` catalog. Community signal is sparse and unverifiable.
- **Growth**: SEO/CRO/ads/email each have specialised SaaS markets but few Claude-Code-native plugins. Mostly MCP-server territory, not skill territory.

Auditing them against the whole marketplace would mean comparing apples (our workflow-integrated commands) to oranges (vertical SaaS). The honest comparator for batch 2 is narrower: **what does Anthropic itself ship in `anthropics/claude-plugins-official` that overlaps?** Anything broader is out of scope for v2 and gets deferred to a hypothetical batch 3.

## Methodology — v2 delta from batch 1

### 1. Single comparator source

For each pack in scope, the only alternative considered is one already listed in [`anthropics/claude-plugins-official`](https://github.com/anthropics/claude-plugins-official). No web-wide search, no community plugins, no vendor-published skills outside that repo.

Rationale: the question batch 2 answers is _"if Anthropic's own first-party catalog already covers this, why do we ship our own?"_ — not _"is there anyone in the world doing this better?"_.

### 2. Verdict matrix simplifies to 3 buckets

Batch 1 used 4 verdicts (`KEEP-OURS` / `POINT-TO-VENDOR` / `POINT-TO-COMMUNITY` / `GAP-OUTSCOPE-POINTER`). Batch 2 collapses to 3:

| Verdict | Meaning | Action on the pack |
|---------|---------|--------------------|
| `KEEP-OURS` | No plugin in the official catalog overlaps the pack's intent. | No change. |
| `POINT-TO-ANTHROPIC-PLUGIN` | An official catalog plugin covers the same intent end-to-end. | Add `## See also` to the agent/command/skill file. Keep our pack (workflow integration value). |
| `ADJACENT-POINTER` | An official catalog plugin covers part of the pack's surface but not all of it. | Add `## See also` with explicit scope caveat. Keep our pack. |

No removal proposals in batch 2 — pointer-only outcome. Removals stay deferred to the future v2.0 cleanup (per `spec.md` Phase 5).

### 3. No vendor-neutrality filter required

Anthropic is by definition the home ecosystem (already noted in batch 1's `qa-review` and `dev-frontend-design` verdicts). The filter from `feedback_plugin_curation_vendor_neutrality` does not apply when the source IS Anthropic.

### 4. No adoption-count check

Batch 1's _"≥3 real-product repos via `gh search code`"_ bar exists to validate non-vendor community skills. Catalog membership in `anthropics/claude-plugins-official` is canonical-by-construction — no further adoption proof needed.

### 5. Rubric — keep or drop?

`spec.md` § Methodology defines a 4-axis numeric rubric (Integration value / Marketplace alternative depth / Maintenance cost / Usage signal, total 4-12) that none of the batch 1 pilots actually used. Batch 1 produced qualitative verdicts directly. Batch 2 explicitly **drops the numeric rubric** and writes per-pack qualitative rationale — same as batch 1 in practice.

If a future batch (3+) audits against the broader marketplace again, the rubric can be revived. This is a v2-specific simplification, not a methodology-wide change.

## Pre-audit hygiene (run before each pilot)

Both domains exhibit count drift between `spec.md` and the live tree. Verify counts before the pilot — do **not** trust `spec.md` as the authoritative inventory.

```bash
# Legal — spec.md says 5+5+0, actual = 5 commands + 4 agents
ls .claude/commands/legal/ | wc -l       # expect 5
ls .claude/agents/ | grep ^legal- | wc -l # actual is 4 (one command unpaired)

# Growth — spec.md says 11+11+0, actual = 11 commands + 6 agents
ls .claude/commands/growth/ | wc -l       # expect 11
ls .claude/agents/ | grep ^growth- | wc -l # actual is 6 (5 commands unpaired)
```

The drift does not block batch 2 — it just means the pilot inventories must enumerate from the filesystem, not from `spec.md`. Surfacing this drift in each pilot's "Honest limits" section is mandatory.

## Per-domain plan

### Legal pilot — `legal-vs-anthropic-pilot-<date>.md`

**Scope**: all 5 commands in `.claude/commands/legal/` (`legal-docs`, `legal-payment`, `legal-privacy-policy`, `legal-rgpd`, `legal-terms-of-service`), each evaluated alongside its paired agent when one exists.

**Hypothesis**: Anthropic's official catalog is engineering-focused (code-review, frontend-design, pyright-lsp, greptile…). Legal compliance content is unlikely to appear. **Expected outcome: all 5 KEEP-OURS.**

**Execution steps**:

1. Inventory `anthropics/claude-plugins-official` plugins (list `plugins/` directory contents, classify each by primary intent in one line).
2. For each of the 5 legal packs:
   a. Read the pack's command + agent definition to extract its stated intent.
   b. Scan the inventory from step 1 for any plugin whose stated purpose touches the same intent (legal review, compliance, privacy, payment regs, ToS drafting).
   c. Assign verdict per the 3-bucket matrix.
3. Capture rationale per pack (one short paragraph + plugin link if applicable).
4. Honest limits: note the count drift; note that legal-specific marketplaces (Sushegaad, Claude Cowork) are out of scope by design.

**Risk to watch**: an Anthropic plugin like `code-review` may touch _some_ compliance concerns (e.g. PII leak detection) without being a legal pack. That's `ADJACENT-POINTER`, not `POINT-TO-ANTHROPIC-PLUGIN`.

### Growth pilot — `growth-vs-anthropic-pilot-<date>.md`

**Scope**: all 11 commands in `.claude/commands/growth/` (`growth-ab-test`, `growth-analytics`, `growth-app-store-analytics`, `growth-cro`, `growth-email`, `growth-funnel`, `growth-landing`, `growth-localization`, `growth-onboarding`, `growth-retention`, `growth-seo`), each evaluated alongside its paired agent when one exists.

**Hypothesis**: Anthropic's catalog is engineering-focused, so most growth packs land `KEEP-OURS`. Possible overlap candidates:

- `growth-landing` — Anthropic ships `frontend-design`; pure landing-page work might be `ADJACENT-POINTER` (visual design overlap but no growth/CRO framing in `frontend-design`).
- `growth-analytics` — if Anthropic ships an instrumentation/telemetry plugin, watch for overlap.
- `growth-localization` — i18n is engineering-adjacent; if a plugin exists, evaluate.

**Expected outcome**: 9-11 `KEEP-OURS`, 0-2 `ADJACENT-POINTER`, 0 `POINT-TO-ANTHROPIC-PLUGIN`.

**Execution steps**: identical to legal pilot, just over 11 packs instead of 5.

**Risk to watch**: temptation to point growth packs at engineering plugins (`frontend-design`) when the framing genuinely differs. Bias toward `KEEP-OURS` when in doubt; pointers must have clear caveats about what is and is not covered.
